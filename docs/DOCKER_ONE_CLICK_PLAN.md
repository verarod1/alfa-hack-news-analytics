# План единого воспроизводимого запуска Docker

Дата: 26.10.2026. Статус: план по результатам изучения исходников; реализация не выполнена.

## Цель и границы

После установки Docker Desktop с Linux containers и однократной подготовки разрешённых CSV/настроек пользователь запускает `start.cmd` двойным щелчком на Windows либо `./start.sh` на Linux/macOS. Скрипт проверяет окружение, собирает образы, готовит БД, запускает компоненты, проверяет приложение и показывает адрес `/demo`. Python, Node и PostgreSQL на компьютере не нужны.

Источник истины — `docker-compose.yml`, а скрипты лишь вызывают общий сценарий Compose. Для уже подготовленного окружения целевая команда — `docker compose up --build --wait`. Её работоспособность с одноразовыми init-сервисами нужно проверить на закреплённой минимальной версии Compose.

Воспроизводимость означает фиксированный код, зависимости, порядок подготовки и ожидаемые проверки. Содержимое живых RSS и ответы внешней LLM не будут одинаковыми при каждом запуске. Первый запуск требует сети для образов, пакетов и, при включённом RAG, embedding-модели.

## Что уже существует и что мешает

- Compose уже содержит PostgreSQL, FastAPI, React/nginx, analysis-worker, news-collector и необязательный ranking-worker. Очередь анализов хранится в PostgreSQL; добавлять Redis/Celery для этой задачи не требуется. Chroma используется как встроенная файловая БД, а не отдельный сервер.
- Схемы `backend/db/schema.sql`, `mvp.sql` и обновление `upgrade_mvp_v2.sql` применяются вручную. `db:healthy` сейчас означает доступность PostgreSQL, но не наличие таблиц.
- `backend/scripts/import_csv.py` делает атомарный импорт с блокировкой, но повторный запуск на заполненных таблицах заканчивается ошибкой. Просто добавить эту команду в каждый старт недостаточно.
- Три необходимые CSV присутствуют локально в `data/raw/`, но исключены из Git. Чистый checkout не содержит компании для рабочего демо.
- `GET /health` в `backend/app/api/main.py` возвращает успех без проверки БД. У API и frontend нет healthcheck, frontend зависит только от факта запуска backend.
- `frontend/Dockerfile` использует `npm install`, хотя есть package-lock. Базовые образы `python:3.11-slim`, `node:20-alpine`, `nginx:alpine`, `postgres:16` имеют изменяемые теги.
- Python-зависимости уже ограничены версиями через `-c requirements.lock`; lock не игнорируется. Однако в нём нет хешей артефактов, а комментарий сообщает о проверке Linux ARM64, не AMD64. Доступность всех пакетов и CPU-wheel torch на целевых архитектурах ещё требуется подтвердить сборкой.
- В backend нет writable mount для model_cache при `HF_HOME=/app/data/model_cache`: родительский `/app/data` read-only. У воркеров model_cache writable. Наборы mounts различаются, backend дополнительно монтирует data/cache.
- Фиксированные `container_name` мешают независимому второму Compose-проекту. Общие bind-каталоги кэшей также не изолируются одним `-p`.
- ML по умолчанию выключен. Analysis-worker не обрабатывает очередь без конфигурации; ранкер дополнительно требует профиль ranking и NEWS_RANK_ENABLED. Для полного AI-сценария нужны внешний LLM endpoint, ключ и выбранные модели.
- RAG фактически ленивый: первый поиск индексирует PDF, скачивает модель при отсутствии кэша и может вызвать внешний OCR для сканов. Это входит в путь ML-запроса с ограниченным таймаутом. README и ML-инструкции местами противоречат друг другу о ручном/автоматическом запуске.
- В репозитории нет отслеживаемого CI workflow в `.github`. Существующий runner интеграционных тестов требует локальных PostgreSQL binaries и Unix socket.

## Порядок реализации

### 1. Зафиксировать сценарии и конфигурацию

Основной сценарий — реальное приложение с предоставленными CSV. Отсутствие CSV при первой подготовке должно давать понятную ошибку до объявления готовности. Не подменять их вымышленными компаниями.

Предусмотреть базовый запуск без LLM и явное включение AI через конфигурацию. Отдельный тестовый сценарий использует маленькие искусственные CSV и тестовый ML-адаптер только в изолированном тестовом проекте. В UI/выводе запуска различать «приложение готово» и «AI включён».

Привести `.env.example` к одному набору параметров. Launcher создаёт `.env` только при отсутствии и генерирует локальный пароль PostgreSQL; существующий файл не перезаписывает. Проверяет необходимые файлы, режим Linux containers, Compose, порты, настройки выбранного режима. Не выводит секреты. Для локального запуска подключение init и runtime должно вести в одну БД Compose; внешнюю БД не инициализировать автоматически.

Результат: точный контракт первого и повторного запуска, без обязательного локального Python/Node.

### 2. Сделать сборки предсказуемыми

- Перевести frontend на `npm ci`, проверить соответствие package.json и lockfile.
- Выбрать поддерживаемую версию Node, совместимую с engines в lockfile; закрепить точные версии и digests базовых образов. Для нескольких архитектур использовать подходящие multi-platform digests.
- Проверить Python lock чистой сборкой Linux AMD64 и ARM64; при различиях разделить ограничения по платформам. Закрепить CPU-вариант torch и источник пакетов, исключить случайную CUDA-загрузку. Для строгой фиксации артефактов подготовить lock с хешами.
- Backend и воркеры должны использовать один и тот же собранный образ; проверить отсутствие повторных тяжёлых сборок. Сохранить `.dockerignore`, дополнить frontend исключениями `.env*`, сохранив шаблон при необходимости.
- Отдельная test-стадия/образ включает dev-зависимости; не предполагать, что runtime-образ содержит всё для тестов.

Результат: сборка из чистого checkout без старых образов и кэшей на заявленных платформах.

### 3. Автоматизировать подготовку схемы

Добавить одноразовый сервис `migrate` на backend-образе и versioned migration runner. Он ждёт `db:service_healthy`, использует блокировку, журнал версий и проверки фактической схемы. Для новой БД создаёт raw- и актуальную MVP-схему.

Для существующей БД нужен отдельный путь baseline/upgrade: `upgrade_mvp_v2.sql` нельзя запускать до появления таблиц, а `CREATE TABLE IF NOT EXISTS` не обновляет существующие колонки. Неподдерживаемую старую схему останавливать с объяснением; не удалять данные. Учесть уже имеющиеся BEGIN/COMMIT в SQL при выборе транзакционной модели runner.

API, сборщик и воркеры должны ждать `migrate:service_completed_successfully`. Ошибка миграции блокирует запуск зависимых сервисов. Не ограничиваться `/docker-entrypoint-initdb.d`: задача включает обновление уже созданного volume.

Результат: первый запуск создаёт схему; повторный безопасно проверяет актуальность; сломанная миграция не маскируется.

### 4. Автоматизировать начальные данные

Добавить `bootstrap` после migrate. Переиспользовать транзакционный импортёр, добавив учёт завершённого импорта и идентификатора/контрольных сумм набора. Успешно загруженный набор при повторном старте пропускается. Частично заполненная старая БД и изменённые CSV требуют отдельного диагностируемого действия, а не `--replace`.

Маркер успешного импорта фиксировать в одной транзакции с данными. После импорта проверить наличие всех трёх demo-company ID и шести профилей CEO/CFO. Для существующего набора без маркера предусмотреть проверяемое принятие baseline.

Можно загрузить сохранённые официальные новости существующим import_news_fixtures.py без дублей; сохранять настоящие даты. Для стабильной проверки обращаться к фиксированным news ID: со временем эти новости могут скрыться из обычной ленты из-за NEWS_MAX_AGE_DAYS. Живые RSS не использовать как обязательное условие успешного bootstrap.

Результат: после первого старта доступны компании, а повторный старт не дублирует и не заменяет данные.

### 5. Унифицировать постоянное состояние и ML

Оставить входные CSV/PDF read-only. PostgreSQL, Chroma, OCR и model_cache хранить в именованных volumes проекта с одинаковыми путями у всех потребителей. Если уже есть полезные bind-кэши, предусмотреть явный перенос/режим совместимости: простая смена mounts не перенесёт содержимое сама.

Убрать фиксированные container_name. Разные Compose project names должны получать независимые volumes; исходные данные могут быть общими только read-only, внешние порты — различаться.

При включённом AI добавить отдельный этап подготовки модели/RAG, чтобы скачивание и OCR не происходили неожиданно в первом коротком API-запросе. Закрепить revision embedding-модели и учитывать его в идентичности индекса/кэша. Для большого числа PDF обрабатывать все оставшиеся пакеты: текущий ensure_indexed имеет limit=10. Отсутствие PDF допустимо для режима без банковского RAG, а не должно выдаваться за подготовленный индекс.

Фоновое ранжирование и OCR, требующие внешних вызовов, включать явно выбранным режимом. Обычные healthchecks не вызывают LLM/OCR. Сохранить один analysis-worker и один ranking-worker до отдельной проверки масштабирования.

Результат: кэши переживают пересоздание контейнеров и доступны для записи; AI-режим имеет понятную подготовку и статус.

### 6. Добавить проверки готовности и кнопку запуска

Сохранить `/health` как проверку процесса, добавить `/ready` для подключения к БД, версии схемы и завершения обязательного bootstrap. Готовность AI отражать отдельно от базовой доступности API.

Добавить healthchecks backend и frontend; frontend проверять также через nginx → API. Воркерам добавить наблюдаемый статус последнего цикла/heartbeat, не подменяя его одним фактом существования PID. Временный сбой RSS должен быть виден, но не блокировать интерфейс с сохранёнными данными.

Целевая цепочка: db healthy → migrate completed → bootstrap completed → backend/workers → frontend healthy. Подготовка RAG добавляется в AI-режиме перед нужными потребителями.

Создать `start.cmd` + `scripts/start.ps1` для Windows и `start.sh` для Linux/macOS. Они вызывают один Compose-сценарий, ждут готовности с ограничением времени, проверяют `/demo`, роли и профили, открывают браузер после успеха. При ошибке дают имя этапа и команду просмотра логов, сохраняют ненулевой exit code. Проверка Docker должна отличать отсутствие CLI от выключенного daemon. Никакого автоматического `down -v` или удаления чужих volumes.

Результат: двойной щелчок действительно заканчивается рабочим интерфейсом либо понятной причиной отказа.

### 7. Проверить и обновить документацию

Добавить CI на чистом checkout: сборка, unit/mock tests, изолированный Compose-проект с тестовыми CSV и временной БД, smoke-тесты через nginx. Адаптировать PostgreSQL integration runner к тестовому контейнеру либо обеспечить его binaries в отдельном Linux test-образе. Не подключать тесты к пользовательской БД.

Проверить сценарии:

1. Первый запуск с пустыми volumes: схема, импорт, 6 профилей, лента и API доступны без ручного SQL.
2. Повторный запуск и пересоздание контейнеров: записи и кэши сохранены, дублей нет.
3. Нет CSV, повреждён CSV, несовместимая схема, занят порт, Docker выключен: понятная ошибка без ложного успеха.
4. Базовый режим без ключа: UI работает, статус отсутствия AI явный, нет внешних ML-вызовов.
5. Тестовый AI: queued → completed, чат и ранжирование на контролируемом адаптере. Реальный провайдер проверяется отдельно после его настройки.
6. RAG с пустым и прогретым кэшем, PDF со слоем текста и сканом, более 10 PDF; отсутствие повторного OCR для неизменённых документов.
7. Два проекта одновременно с разными портами: нет конфликтов имён и общего writable состояния.
8. Чистая сборка AMD64 и ARM64; отдельный запуск Windows Docker Desktop. Указать фактически проверенные версии и ресурсные требования по измерениям.

Сократить README до одного основного запуска и ссылки на подробности. Обновить DOCKER_CLEAN_MACHINE.md, README_ML_CORE.md и связанные руководства: убрать противоречия о ручных миграциях, сборщике, AI и RAG. Задокументировать остановку с сохранением данных, резервное копирование и отдельное осознанное обновление датасета.

## Приоритет

Первый этап реализации: сборка → миграции → bootstrap → mounts → readiness → launcher. Это даёт воспроизводимый базовый запуск. Затем подготовка полного AI/RAG-режима и автоматические проверки всех целевых платформ. Не смешивать завершение инфраструктуры с обещанием одинакового качества внешней LLM.

## Что проверено при подготовке плана

Изучены Compose, Dockerfiles, lockfiles, настройки, схема/upgrade SQL, импортёры, фоновые worker-циклы, API health, frontend proxy/API client, ML gateway, RAG, инструкции и тестовый runner. Содержимое секретного `.env` не выводилось. Код приложения и конфигурация не изменялись.

Docker CLI не найден в PATH текущего окружения. Поэтому `compose config`, сборка, старт контейнеров и интеграционный прогон здесь не выполнены. Указанный в старой документации успешный прогон на Mac — запись репозитория, а не проверка в этой сессии.
