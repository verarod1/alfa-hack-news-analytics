# Ручной сбор реальных новостей

## Версия и границы работы

Реализация в `feature/backend-mvp`, без объединения с `feature/ml-core` и без изменения `main`. Для совместимости изучена удалённая ML-ветка `49a665b` от 25 октября 2026 года. ML-адаптер, RAG, модели, PyTorch и текущие API не переписаны. Сборщик не создаёт схемы, не читает CSV/PDF и не меняет исходные таблицы.

Разрешены только три источника:

| Код | RSS | Способ получения текста |
| --- | --- | --- |
| cbr | https://www.cbr.ru/rss/RssPress | Текст RSS; публикации без достаточного текста пропускаются. |
| minfin | https://minfin.gov.ru/rss_news?mod=news&lim=50 | Ссылка RSS → официальный HTML → отдельный extractor. |
| fns | https://www.nalog.gov.ru/rn77/rss/ | Ссылка RSS → официальный HTML → отдельный extractor. |

Условия использования и атрибуции: [аудит](NEWS_SOURCES_AUDIT.md). Интерфейс должен показывать название источника и ссылку; для материалов Минфина учитывать CC BY 4.0, исключения и атрибуцию лицензии. Новости регуляторов не становятся официальной позицией Альфа-Банка.

## Как работает

1. CLI читает настройки, выбирает разрешённые источники и создаёт один ограниченный HTTP-клиент.
2. Перед запросами проверяет robots.txt конкретного хоста и пути с учётом User-Agent, wildcard и Crawl-delay. 404 robots означает отсутствие правил по этому URL; 401/403/429/5xx, таймаут или HTML вместо robots останавливают источник.
3. Скачивает RSS с проверкой TLS, ограничением размера, времени и редиректов. DNS-адреса должны быть публичными; соединение закреплено за проверенным IP с сохранением Host/SNI и проверки сертификата. Proxy-переменные не используются. Неизвестные хосты, credentials, произвольные порты, внутренние пути и HTTPS→HTTP не допускаются.
4. Проверяет XML без DTD/entity declarations, извлекает максимум `limit` элементов на источник. Заголовок очищается, дата приводится к UTC. Неизвестная дата остаётся null с предупреждением; некорректная дата отклоняется.
5. Для Минфина/ФНС получает только разрешённые страницы публикаций. Проверяет h1, извлекает текст из конкретных контейнеров, убирает скрипты, меню, формы и блоки социальных ссылок. При неизвестной разметке пропускает страницу, а не сохраняет весь body. Вложенные p не дублируют текст.
6. Применяет необязательные фильтры давности и ключевых подстрок. Это отбор для загрузки, а не персональный relevance. Старые записи в PostgreSQL не удаляются.
7. Собирает существующий `NewsInput`: стабильный строковый ID, source_id/name, permalink статьи, text, published_at и `is_synthetic=false`. ID зависит от источника и URL, а не изменяемого заголовка или RSS GUID. HTTP-ссылки известных официальных хостов нормализуются в HTTPS; остальные редиректы отдельно проверяются.
8. Без `--dry-run` вызывает `news_service.save_news`. Повтор неизменённой записи использует прежний ID. Исправленный текст с тем же ID даёт NEWS_CONFLICT: старая запись не меняется, сбор остальных продолжается. Автоматического UPDATE/удаления и переиндексации старых анализов нет.
9. Выводит JSON-отчёт с ID, названием, URL, датой, длиной текста, счётчиками, безопасными кодами ошибок и Retry-After. Сырые исключения/HTML/DSN не печатаются. Полный текст доступен через существующий API после сохранения.

В отчёте `stored_or_existing` — успешное сохранение **или** уже существующая идентичная запись, это не число новых INSERT. `accepted` включает валидную публикацию, даже если её сохранение встретило конфликт. `rss_total` — число элементов ответа, `inspected` — сколько рассмотрено с учётом limit. EMPTY_FEED — предупреждение, не имитация успешного получения публикации.

При 401/403/429/5xx и сетевой недоступности дальнейшие статьи источника в этом запуске не запрашиваются. Нет автоматических повторов/обхода защиты; Retry-After виден оператору. При недоступной БД завершается весь запуск. Остальные ошибки отдельных публикаций не уничтожают уже сохранённые новости. Процесс завершается: 0 — без ошибок (в том числе пустой RSS), 1 — частичный/неуспешный сбор, 2 — некорректная конфигурация/параметры.

## Локальный запуск

Из корня проекта с активированным Python-окружением и установленными `backend/requirements-dev.txt`. Дополнительная небольшая зависимость `truststore==0.10.5` использует системные доверенные сертификаты; версия уже зафиксирована в requirements.lock.

```sh
# Сеть разрешена, БД не используется:
python backend/scripts/collect_news.py --source cbr --limit 3 --dry-run
python backend/scripts/collect_news.py --source minfin --limit 2 --dry-run
python backend/scripts/collect_news.py --source fns --limit 2 --dry-run
python backend/scripts/collect_news.py --source all --limit 2 --dry-run

# Проверенная целевая БД уже имеет backend/db/mvp.sql:
python backend/scripts/collect_news.py --source cbr --limit 3

# OR по подстрокам заголовка/текста; 0 отключает фильтр давности:
python backend/scripts/collect_news.py --source all --limit 5 --keywords 'ставк,налог,тамож' --max-age-days 30 --dry-run
```

Сохранение в рабочую PostgreSQL и применение схем отдельно согласуются. На этом этапе реальные сетевые проверки выполнены только с dry-run/извлечением текста в памяти, без записи в рабочую БД. SQL и CSV импортёры автоматически не вызываются.

## Настройки

| Переменная | По умолчанию и назначение |
| --- | --- |
| NEWS_SOURCES | cbr,minfin,fns — включённые источники; `all` означает только включённые. |
| NEWS_CBR_RSS_URL | https://www.cbr.ru/rss/RssPress |
| NEWS_MINFIN_RSS_URL | https://minfin.gov.ru/rss_news?mod=news&lim=50 |
| NEWS_FNS_RSS_URL | https://www.nalog.gov.ru/rn77/rss/ |
| NEWS_LIMIT | 10, диапазон 1–100; ограничение на источник, переопределяется CLI. |
| NEWS_TIMEOUT_SECONDS | 20, диапазон 1–60; сетевой timeout и deadline чтения ответа. Разрешение DNS зависит также от системного resolver. |
| NEWS_MAX_RESPONSE_BYTES | 2000000, максимум 5000000. Для robots отдельный предел не более 300000. |
| NEWS_USER_AGENT | AlfaHackNewsCollector/1.0 — честный идентификатор; не подменять браузером для обхода запрета. |
| NEWS_REQUEST_DELAY_SECONDS | 1, диапазон 1–60; минимум между запросами к хосту, с учётом Crawl-delay. |
| NEWS_MAX_AGE_DAYS | 30; 0 отключает, максимум 3650. Дата более чем на сутки в будущем пропускается. |
| NEWS_MIN_TEXT_CHARS | 120, диапазон 40–1000; отсеивает пустую/техническую разметку. |
| NEWS_KEYWORDS | Пусто — без тематического отбора. Подстроки через запятую, OR. |

Адреса каналов дополнительно проверяются против трёх аудированных host/path/query. Это намеренный allowlist: переменная URL не разрешает произвольный сайт или внутренний API. Для нового источника нужен отдельный аудит и адаптер.

Настройки берутся из окружения и существующего `.env`, но `.env` не изменён. Ключи LLM для сборщика не нужны. Без `--source` CLI использует включённый список; автоматического расписания нет.

## Docker и пути данных

```sh
docker compose build backend
docker compose run --rm --no-deps backend python scripts/collect_news.py --source cbr --limit 3 --dry-run

# Только для заранее подготовленной выбранной БД и уже работающего db:
docker compose run --rm --no-deps backend python scripts/collect_news.py --source cbr --limit 3
```

Если backend уже запущен из актуального образа, допустимо `docker compose exec backend python scripts/collect_news.py --source cbr --limit 3 --dry-run`. Старая запущенная версия образа не получает новый код от одного изменения файлов на хосте.

Минимальное изменение Compose: `DATA_DIR: ${DOCKER_DATA_DIR:-/app/data/raw}`. В `.env.example` локальный `DATA_DIR=data/raw`, Docker-путь задаётся отдельно. CSV и PDF не перемещались. Если существующие CSV находятся непосредственно в data/, оставьте для них локальный DATA_DIR=data и DOCKER_DATA_DIR=/app/data. Для парсера эти пути не нужны: он пишет через существующее подключение PostgreSQL.

Структура для совместной работы:

- data/raw/ — исходные CSV;
- data/raw/bank_analytics/ — исходные PDF;
- data/chroma_db/ — предлагаемый постоянный индекс;
- data/rag_cache/ или data/ocr_cache/ — предлагаемый OCR-кэш.

Существующее `./data:/app/data:ro` сохранено. Writable-монтирования Chroma/OCR в этом изменении не добавлены: проверенный ML-код ещё использует /tmp и сам по себе новый volume не заставит его читать постоянный путь. Эти изменения следует согласовать с ML-разработчицей отдельно, сохранив исходные данные read-only. Новые ignore-правила защищают PDF, ChromaDB и кэши от случайного добавления в Git. Перестраивать или очищать RAG парсер не должен.

## Передача новостей в ML

Контракт не менялся. После сохранения:

- `GET /api/v1/news/{id}` возвращает ID, заголовок, текст, дату, источник и synthetic=false;
- `GET /api/v1/feed?company_id=U_81&role=cfo` читает ту же news-таблицу; до ML-оценок — chronological, score=null;
- `AnalysisContext.news` содержит полноценную `NewsResponse`, поэтому `team_ml.adapter.analyze(context)` может использовать сохранённую новость без нового контракта;
- `news_service.get_news(id).model_dump(mode='json')` даёт ML ожидаемый dict; для ограниченной порции можно использовать существующий `news_repository.list_news(limit, offset)` и нормализовать строки через `news_service.news_response`;
- оценку передавать в `news_service.save_relevance(RelevanceAssessment(...))`: company_id/role/news_id, действительный score, reasons, method и method_version. Этот сервис дополнительно проверяет компанию, роль и новость;
- парсер не вызывает ранжировщик, адаптер, чат или process_analyses. Автоматические платные операции отсутствуют.

В `feature/ml-core` функция `rank_news()` уже принимает словари компании/новости и роль. Она не вызывается автоматически основным адаптером и не требует отдельного формата от парсера. ML-разработчице нужно отдельно связать её с ограниченной порцией news и не сохранять выдуманные значения при ошибке генерации. Профиль компании следует брать из Backend, не из второго CSV-маппера.

Для позиции банка остаются обязательными проверенные document/page/quote из BANK_MATERIALS_PATH. Новости ЦБ/Минфина/ФНС не попадают в этот манифест. Источники/дисклеймеры существующих анализов и чата сохранены.

## Совместимость при будущей интеграции веток

На момент проверки в ML-ветке нет файлов сборщика, а docker-compose.yml совпадает с прежним Backend. Возможные ручные конфликты:

- `.env.example`: DATA_DIR уже изменён ML на data/raw; сохранить это значение, добавить DOCKER_DATA_DIR и NEWS_* без потери ML-настроек;
- `.gitignore`: обе ветки добавляют PDF/Chroma, объединить правила и сохранить OCR-кэши;
- `backend/requirements.txt`: ML добавляет torch/LLM/RAG зависимости. Не заменять этот файл целиком нашей версией и не удалять CPU-настройки. Сохранить truststore и проверить общий lock отдельно;
- `docker-compose.yml`: согласовать наш Docker DATA_DIR с будущими writable volumes ML;
- если ML заполняет те же пустые parsers-файлы, сравнить обе реализации до объединения, не перезаписывать автоматически.

Никаких merge/rebase/cherry-pick/commit/push в ходе реализации не выполнялось. Старые документы аудита от 24 октября — исторический срез, текущий статус реализации указан здесь.
