# Как устроен проект alfa-hack-news-analytics

> Исторический срез до исправлений аудита. Актуальные правила, запуск и API: [BACKEND_MVP.md](BACKEND_MVP.md), [API-контракт](api/API_CONTRACT.md).

Состояние кода на 24 октября 2026 года. Документ объясняет текущую локальную
версию проекта, включая незакоммиченный первый эндпоинт. Наличие реализации
в файле не означает, что она уже проверена на рабочей базе или доступна в main.

## 1. Назначение и текущая готовность

Проект предназначен для новостной аналитики с учётом особенностей бизнеса.
Предполагается, что профиль компании и её связи будут давать контекст для
интерпретации новостей. Полная цепочка анализа пока не реализована.

Сейчас подготовлены:

- приложение FastAPI и проверка его доступности;
- SQL-схема компаний, платежей и связей физических лиц с компаниями;
- безопасный импорт трёх CSV и пять изолированных тестов;
- Docker Compose для PostgreSQL, backend и frontend;
- локальная реализация получения профиля компании по ID.

Исправления импортёра опубликованы в ветке `fix/postgres-import-safety`,
коммит `1be5cbd`. В рамках нашей работы эта ветка не вливалась в main.
Файлы первого API остаются локальными незакоммиченными изменениями.

Парсинг новостей, аналитические сервисы и интеграция ML/LLM в просмотренных
файлах ещё не реализованы. Frontend пока содержит стартовую страницу React/Vite.

## 3. Как проходит запрос профиля компании

```text
HTTP GET /api/v1/companies/{company_id}
    → companies.py: обработка запроса
    → company_repository.py: чтение PostgreSQL
    → проверка отсутствия или противоречивых записей
    → company_mapper.py: преобразование полей
    → CompanyResponse: проверка структуры
    → JSON-ответ клиенту
```

Это разделение помогает понимать ответственность кода:

- **Роутер** принимает HTTP-запрос и выбирает ответ или HTTP-ошибку.
- **Репозиторий** знает SQL и обращается к базе.
- **Mapper** переводит названия и значения исходных полей в формат API.
- **Pydantic-схема** задаёт ожидаемые поля и типы ответа.

В текущем эндпоинте отдельный сервисный слой не используется: роутер вызывает
репозиторий и mapper напрямую.

### Точка входа: main.py

`FastAPI(...)` создаёт приложение с названием, описанием и версией.
`app.include_router(companies_router)` подключает маршруты компаний.
`CORSMiddleware` настраивает доступ из браузера; сейчас правила разрешающие,
ориентированы на локальную разработку. Авторизация в этом файле не реализована.

Есть три маршрута:

| Метод и путь | Что делает сейчас |
| --- | --- |
| `GET /health` | Возвращает фиксированный статус работы приложения |
| `GET /api/v1/companies/{company_id}` | Читает и преобразует профиль компании |
| `POST /api/analyze` | Принимает `text` и `company_id`, возвращает заглушку |

`/health` не проверяет PostgreSQL. Успешный ответ этого маршрута не доказывает,
что база доступна. `/api/analyze` пока не вызывает модель и не анализирует новость.

### Роутер companies.py

Роутер имеет префикс `/api/v1/companies`. Функция `get_company()` получает ID
из URL и вызывает `get_company_raw()`.

- Нет записей — HTTP `404`, «Компания не найдена».
- Есть записи с разным содержимым JSON — HTTP `409`, «Найдены разные записи одной компании».
- Одна запись или несколько одинаковых — преобразуется первая запись.

Сравнение касается содержимого записей, а не только совпадения ID. Эндпоинт
самостоятельно не объединяет разные версии компании. Ошибки подключения к БД
здесь отдельно не обрабатываются.

### Репозиторий company_repository.py

Запрос выбирает `raw_data` из `raw_companies` по `synthetic_u` и сортирует
результат по `row_id`. Поэтому порядок записей определён.

Значение ID передаётся параметром `%s`, отдельно от SQL. Оно не вставляется
в текст запроса через форматирование строки.

`with get_connection()` и `with conn.cursor()` управляют соединением и курсором.
Результат — список исходных JSON-объектов, который дальше проверяет роутер.
Новое соединение открывается при каждом вызове; пул подключений не настроен.

### Преобразование company_mapper.py

`map_company()` строит словарь ответа из исходной записи.

| Поле ответа | Откуда берётся |
| --- | --- |
| `id` | `SYNTHETIC_U` |
| `company_name` | Строка «Компания {ID}», настоящее название не извлекается |
| `industry` | `MAINOKVED_CODE`, `MAINOKVED_NAME` |
| `region`, `city` | `REGION`, `CITY` |
| `age_range` | `COMPANY_AGE_YEARS_GRADATION` |
| `employees_range` | `AMOUNT_WORKERS_FNS_GRADATION` |
| `business_stage` | `ECO_MARK_LABEL` |
| `client_type` | `CL_TYPE` |
| `revenue.value` | Числовое преобразование `REVENUE_COMPANY` |
| `foreign_trade` | `FTS_FLAG`, `FTS_COUNTRY_NAME` |
| `group_id` | `GROUP_ID` |
| `organization_type`, `ownership_form` | `ORG_TYPE`, `OKFS_NAME` |
| `key_owner_flag` | `NEGATIVEMARK` |
| `employees_spark_range` | `AMOUNT_WORKERS_SPARK_GRADATION` |

Имена полей описывают текущий код; смысл спорных признаков нужно подтвердить
по описанию датасета. Например, соответствие `NEGATIVEMARK` полю `key_owner_flag`
само по себе не подтверждает, что признак действительно означает ключевого владельца.

Вспомогательные функции:

- `normalize()` убирает пробелы по краям и превращает пустое значение в `None`.
- `to_number()` поддерживает запятую в числе, преобразует через Decimal в float;
  обычная ошибка преобразования даёт `None`.
- `to_boolean()` распознаёт `1`/`true` и `0`/`false`; неизвестное значение даёт `None`.

`revenue.unit` пока равен `unconfirmed`: единицы выручки не подтверждены.
Все признаки в `bank_products` пока равны `None`. Нельзя интерпретировать это
как отсутствие продукта: `null` означает, что значение здесь ещё не определено.

### Схемы company.py

Pydantic-модели `Industry`, `Revenue`, `ForeignTrade`, `BankProducts` и
`CompanyResponse` описывают вложенный JSON-ответ. Запись `str | None` означает,
что допустимы строка или отсутствие значения. В JSON `None` превращается в `null`.
`Field(default_factory=list)` создаёт отдельный список для каждого объекта.

`response_model=CompanyResponse` позволяет FastAPI проверять и формировать ответ
по схеме. Схема не вычисляет бизнес-признаки и не подтверждает качество исходных данных.

## 4. Хранение данных в PostgreSQL

`backend/db/schema.sql` описывает три таблицы:

| Таблица | Основные поля | Смысл |
| --- | --- | --- |
| `raw_companies` | `row_id`, `synthetic_u`, `raw_data` | Исходные профили компаний |
| `raw_payments` | `row_id`, `payer`, `beneficiary`, `pay_amt`, `pay_cnt` | Платёжные данные |
| `raw_person_links` | `row_id`, `synthetic_f`, `synthetic_u`, `raw_data` | Связи физлиц с компаниями |

`row_id` — автоматически выдаваемый первичный ключ строки. Он отличается от
идентификатора компании: одной компании могут соответствовать несколько строк.
`pay_amt` имеет тип NUMERIC, `pay_cnt` — BIGINT.

JSONB хранит поля исходной строки компаний и связей. Это позволяет сохранить
признаки, которые пока не вынесены в отдельные колонки. Сохраняются значения,
а не исходное форматирование CSV или порядок ключей. У платежей JSONB-колонки нет.

Индексы подготовлены по ID компании, плательщику, получателю, ID физлица и группы.
Текущий запрос профиля соответствует индексу `raw_companies(synthetic_u)`.
Ускорение конкретных запросов под нагрузкой ещё не измерялось.

Уникальность `synthetic_u` не установлена: в локальном CSV найдены повторы.
Внешние ключи между исходными таблицами тоже не заданы. Схема пока хранит исходный
набор, а не гарантирует полную согласованность всех связей.

`CREATE TABLE IF NOT EXISTS` не изменяет существующую таблицу и не проверяет,
что её колонки совпадают с описанием. Автоматической миграции схемы здесь нет.

## 5. Как устроен import_csv.py

Импортёр — отдельный скрипт, а не API-эндпоинт. Он читает:

| CSV | Обязательные колонки |
| --- | --- |
| `df_Uid_data_hack.csv` | `SYNTHETIC_U` |
| `df_Uid_payment_hack.csv` | `PAYER`, `BENEFICIARY`, `PAY_AMT`, `PAY_CNT` |
| `df_Fid_Uid_link_hack.csv` | `SYNTHETIC_F`, `SYNTHETIC_U` |

### Основные функции

| Функция | Ответственность |
| --- | --- |
| `get_connection()` | Читает настройки и открывает PostgreSQL-соединение |
| `clean()` | Убирает пробелы, пустую строку превращает в `None` |
| `payment_values()` | Проверяет сумму и количество платежей |
| `read_csv()` | Проверяет файл и выдаёт строки по одной |
| `import_companies()` | Передаёт компании в PostgreSQL через COPY |
| `import_payments()` | Передаёт платежи с Decimal и целым количеством |
| `import_person_links()` | Передаёт связи и исходные поля в JSONB |
| `run_import()` | Управляет защитой от повторного импорта и транзакцией |
| `main()` | Разбирает аргументы, проверяет файлы, запускает импорт и сообщает результат |

Собственный класс `ImportError` здесь означает ошибку данных или безопасный отказ
от импорта. Он наследуется от ValueError и отличается от встроенной ошибки Python
с таким же названием, которая обычно относится к импорту модулей.

### Порядок выполнения

1. Скрипт читает аргумент `--replace`, если он передан, и выводит предупреждение.
2. Проверяет все три CSV до подключения к БД.
3. Открывает соединение и общую транзакцию.
4. Пытается получить блокировку для координации запусков импортёра.
5. Без `--replace` проверяет, что все три таблицы пусты; иначе останавливается.
6. С `--replace` очищает только три исходные таблицы и сбрасывает их счётчики ID.
7. Загружает три файла через COPY, повторно проверяя строки.
8. После успешного завершения соединения выводит количество загруженных строк.

COPY — механизм PostgreSQL для загрузки набора строк. Файлы читаются последовательно,
целиком в память не помещаются. Они просматриваются дважды: до подключения и при загрузке.
Исходные CSV нельзя менять во время запуска, если нужен согласованный набор данных.

### Проверка данных

CSV ожидается в UTF-8, допускается BOM; разделитель — точка с запятой.
Проверяются наличие файла, заголовки, обязательные колонки, количество полей,
пустые идентификаторы, нулевые символы и ошибки формата/кодировки.

Сумма PAY_AMT преобразуется в Decimal; NaN и бесконечность запрещены.
PAY_CNT должен быть целым числом в диапазоне BIGINT. Пустые сумма и количество
разрешены как NULL. Отрицательные значения отдельно не запрещаются: соответствующее
бизнес-правило пока не задано.

SQL-идентификаторы нормализуются через `clean()`. В JSONB компаний и связей
попадают исходные значения полей, включая пробелы и пустые строки.

### Защита существующих данных

Обычный запуск не дописывает строки к существующему набору: если заполнена хотя бы
одна таблица, операция прекращается. Это защита от повторного импорта без попытки
угадать правила уникальности данных.

`--replace` разрешает полную замену только трёх таблиц. Очистка и загрузка входят
в одну транзакцию: ошибка выходит наружу, и драйвер должен откатить операцию.
CASCADE не используется. При замене чтение таблиц может временно блокироваться.

Advisory lock координирует только процессы с тем же ключом в одной базе.
Обычное чтение он не блокирует; сторонние записи без этого механизма не запрещает.
Если другой экземпляр импортёра уже работает, новый запуск сразу завершается.

Код возврата скрипта: `0` при успехе, `1` при обработанной ошибке.
Сообщения драйвера не печатаются напрямую, чтобы не раскрывать DSN, пароль или
содержимое строки. Поэтому ошибка PostgreSQL намеренно сообщается обобщённо.

## 6. Подключение и переменные окружения

В проекте сейчас две функции `get_connection()`. Это временное разделение:
импортёр опубликован отдельно, а `app/database.py` относится к локальному API.
Отдельного `backend/db_connection.py` в итоговой реализации нет.

| Настройка | Импортёр | Локальная реализация API |
| --- | --- | --- |
| `DATABASE_URL` | Имеет приоритет | Имеет приоритет |
| `POSTGRES_PASSWORD` | Нужен без DATABASE_URL | Нужен без DATABASE_URL |
| `POSTGRES_HOST`, `POSTGRES_PORT`, `POSTGRES_DB`, `POSTGRES_USER` | Используются с локальными значениями по умолчанию | Пока не используются: fallback фиксирован в коде |
| Таймаут подключения | 10 секунд | Явно не задан |

Обе реализации читают корневой `.env` через python-dotenv, не подменяя уже заданные
переменные процесса. В локальном fallback используются `127.0.0.1:5433`, база
`alfa_news`, пользователь `alfa_user`.

`DATA_DIR` задаёт каталог CSV. Относительный путь считается от текущего рабочего
каталога; без переопределения скрипт использует `data/` относительно корня проекта.

В Compose backend получает DATABASE_URL с адресом `db:5432`.
DOCKER_DATABASE_URL позволяет переопределить эту строку, например для пароля
со специальными символами, которые требуют URL-кодирования. Сам POSTGRES_PASSWORD
для PostgreSQL должен оставаться исходным, без такого кодирования.

LLM-переменные из `.env.example` пока являются настройками будущей интеграции;
просмотренный `/api/analyze` их не использует. Наличие библиотеки в requirements
не означает, что соответствующая функциональность уже написана.

## 7. Docker и запуск

Compose описывает три сервиса:

- `db`: PostgreSQL 16. Порт хоста `127.0.0.1:5433` направлен на порт контейнера 5432.
  Именованный volume `postgres_data` хранит данные между пересозданиями контейнера,
  пока сам volume не удалён. Healthcheck использует `pg_isready`.
- `backend`: Python 3.11 и Uvicorn, приложение `app.api.main:app`.
  Ждёт готовности db; каталог `./data` подключён как `/app/data`.
- `frontend`: сборка React/Vite через Node.js, раздача файлов через Nginx.
  Зависимость от backend не является отдельной проверкой готовности HTTP API.

Compose не применяет `backend/db/schema.sql` автоматически: каталог SQL не подключён
к init-скриптам PostgreSQL. Создание схемы — отдельный шаг с записью в базу,
который нельзя считать выполненным только по наличию Compose.

Команды ниже приведены для объяснения; при подготовке документа они не выполнялись.
После установки зависимостей, настройки окружения и подготовки нужной БД:

```sh
# Из корня проекта, в активированном виртуальном окружении.
python -m uvicorn app.api.main:app --app-dir backend --reload
```

По умолчанию API доступен на `http://localhost:8000`, Swagger — на `/docs`.
Локальный эндпоинт компаний требует наличия незакоммиченных файлов API.

```sh
# Реальный импорт: записывает данные в выбранную БД.
python backend/scripts/import_csv.py

# Только справка, без подключения к PostgreSQL.
python backend/scripts/import_csv.py --help
```

Основная инструкция Docker-запуска находится в README. Изменение пароля в .env
не меняет автоматически пароль базы, уже созданной в существующем volume.

## 8. Тесты и границы проверки

Запуск без рабочей PostgreSQL:

```sh
python -B -m unittest discover -s backend/tests -v
```

В текущем окружении также можно явно использовать `backend/.venv/bin/python`.

| Тест | Что проверяет |
| --- | --- |
| `test_small_csv_is_processed_successfully` | Обработку компании, нормализацию ID и сохранение исходных значений в JSON |
| `test_invalid_csv_is_rejected_before_connection` | Ошибки CSV и чисел до подключения, даже с --replace |
| `test_existing_data_or_running_import_prevents_changes` | Отказ от загрузки/очистки при существующих данных или занятой блокировке |

Используются TemporaryDirectory и стандартный unittest.mock. Вызов настоящего
